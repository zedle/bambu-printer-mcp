# Changelog

## Unreleased

### Merged from upstream 1.1.28–1.1.31
- Dependency fixes: basic-ftp 6.2.3, mqtt 5.16.1, proxy-addr 2.0.8.
- X2D native printing and controls on x86-64 Linux (`bambu-printer-mcp-native-setup`). Linux X2D stop and heater-off also go out over MQTT at once, bounded by `BAMBU_EMERGENCY_MQTT_TIMEOUT_MS`; heater-off there is the same Studio-form command the native route sends. Printers behind the FULU bridge never get this unsigned LAN copy, since they refuse it.
- HMS codes Bambu lists for a printer's serial prefix without text (the generated hidden-HMS table, including the H2C's `31B`) come back as warnings that say so, only with the printer's own returned serial and model; `clear_hms_errors` leaves them alone and shows codes in Bambu's dashed form.
- Remote slicing through an OrcaSlicer API server (`slicer_type` `orca-slicer-api`, `SLICER_API_URL`).
- X2D file forms: OrcaSlicer's `M620.17 T S L-1` preheat and the X2D filament-change banner. `M9711` timelapse capture keeps the H2C, H2D, H2D Pro and X2D and now checks Bambu's exact template parameters (`S11 C10 O0`, extruder, position and height within the machine).
- `nozzle_volume_type` (`standard`, `high_flow`; default `BAMBU_NOZZLE_VOLUME_TYPE`) on the slice tools and the print tools that auto-slice, as a shorthand for every extruder's `nozzles[i].flow`: an explicit flow must agree, it can't be combined with `nozzles_from_printer`, and a flow the machine preset doesn't declare is refused.
- Dual-nozzle external spools, upstream's checks on this fork's Bambu Studio encoding: inspection composes each filament's physical nozzle from the selected plate's `filament_map` and `physical_extruder_map` headers (`filamentNozzleIndices`; malformed or contradicting headers fail, and the plate header's `physical_extruder_map` wins over the project default); an external spool picked with `ams_mapping`/`ams_slots` and `use_ams: false` is kept and checked against the nozzle it feeds instead of being replaced; on printers with two usable holders (H2D, H2D Pro, X2D) an external spool needs that binding, while the H2C keeps its one holder (254); an external spool on a dual-nozzle printer needs the printer's per-nozzle `vir_slot` report. Encoding stays Studio's (a single-nozzle printer's holder is 255, AMS-HT units `{unit, 0}`), and external-only bridge prints now send it too: `-1` in `ams_mapping`, the holder in `ams_mapping2`. Heater `T` in a file names one of two physical heaters on two-nozzle printers, whatever the file declares.
- With `BAMBU_REQUIRE_CONFIRMATION=1`, a hidden HMS notice that appears after the print confirmation stops the print until it is started again (and named); unattended prints pass it as a warning, like any serious or common entry.
- Kept from this fork: the idle-hotend `M104 T<extruder> S<target> N0` form only (upstream also took `N1` and `M109 … N`).

### Added
- Slice the H2C's right extruder as Hybrid (several nozzle flows from its hotend rack): `nozzles[i].flow` takes `Hybrid`, and `nozzles[i].hotends` counts a rack extruder's hotends by flow (`{"Standard": 3, "High Flow": 3}`). With `nozzles_from_printer` the counts come from the printer's normal mounted and rack hotends of the slice diameter, and a rack holding several flows slices as Hybrid, as Bambu Studio's printer sync does; an explicit single flow keeps only that flow's hotends and is refused when the printer has none. The setup goes to the CLI as `--nozzle-volume-type`, `--extruder-nozzle-count` and `--extruder-nozzle-volume-type` (Studio's sub-nozzle order), the slicer then gives each filament a flow and hotend, and a filament needs settings for at least one of the Hybrid extruder's flows. Hybrid without a rack, without hotends of two flows, with more hotends than the rack holds or with a flow the extruder's profiles lack is refused. Validated offline with the Bambu Studio 02.08.02.61 CLI: the Hybrid slice passes the MCP's inspection and printer-state checks against a recorded H2C report; no print was started.
- Inspect and check H2C jobs sliced with a Hybrid right extruder (Bambu Studio's `nozzle_volume_type` value `Hybrid`, enum `nvtHybrid`: a hotend rack mixing flows). The plate header then lists the selected variant rows once per flow (`printer_extruder_id = 1,2,2`); each extruder's hotend material is resolved through its own rows, which must agree. Before printing, every flow the Hybrid extruder plans (`slice_info.config` `<nozzle>`) needs a matching mounted or rack hotend, filament prohibitions use the hotend each filament is sliced for, and Hybrid is refused on an extruder without a rack or on a file without a nozzle plan. Checked against a Hybrid job sliced offline with the Bambu Studio 02.08.02.61 CLI.
- Ask an H2C which rack hotend each filament gets before a job that prints on its right (hotend-rack) extruder, as Bambu Studio does: `get_auto_nozzle_mapping` (Studio's V0 body: filament change order, `ams_id << 8 \| slot` tray codes, each used filament's nozzle group, diameter, flow and tray, the printer's normal mounted and rack hotends with the mounted one named by its `tar_id`; V1 `group_info` for dynamic filament maps), sent on the signed bridge path or the direct LAN client and matched by sequence id. The answer's table goes out as `nozzle_mapping` (BambuNetwork prints and the LAN `project_file`) and the result lists it as `nozzleMapping` with Studio's hotend labels (L, R, R<n>). A `fail`/`failed` answer (with the firmware's reason, e.g. code 8 "the hotend rack is full"), an empty table, or a table that puts a filament on a hotend the printer doesn't report or of another diameter or flow stops the print. No answer within `BAMBU_NOZZLE_MAPPING_MS` (default 15 s) is reported in `hmsWarnings` and the job is sent without a mapping, as before. Rack support is the report's `fun` bit 60.
- Match an H2C job's right-side hotends against the mounted hotend and the rack from the sliced plan (`slice_info.config` `<nozzle>` entries, now part of `inspect_print_file`'s result as `nozzlePlan`): each planned diameter and flow needs a normal hotend, with Studio's advice when none matches (calibrate the rack, refresh the hotend information, or re-slice); planning more hotends of a kind than are fitted, or ones whose information is unreliable, is a warning, as in Studio.
- Offer the H2D Pro as `bambu_model` `h2dpro` on every tool that takes a model (slicing, printing, uploads, heating, filament lookup) and in the model prompt. It slices with Bambu Studio's `Bambu Lab H2D Pro <d> nozzle` machine preset and its `@BBL H2DP` filament presets, and prints on the H2 `project_file` route; the printer's identity (model id `O1E`, serial prefix `239`) was already recognised.
- Slice for dual-nozzle printers whose nozzles differ (H2D, H2D Pro, H2C, X2D). `slice_stl` and `slice_with_template` take `nozzles` (per extruder, left first: diameter, flow, hotend material), `filament_map` (the extruder per filament slot, written as Bambu Studio's manual map), `filament_sources` and `nozzles_from_printer` (read the mounted nozzles and the AMS / external holder feeds from a fresh printer report). Each flow is checked against that extruder's variants in the installed profiles, `nozzle_type` rows are set per owning extruder, and a filament mapped to a nozzle its AMS or holder can't feed, a mixed-diameter request, an unprintable filament type or a filament without settings for the nozzle variant is refused before the CLI runs. Validated offline with Bambu Studio 02.08.02.61: a two-colour H2C slice (left High Flow tungsten carbide, right Standard hardened steel) matches the hand-patched profiles of jobs that printed, and passes the MCP's print inspection; no print was started.

### Changed
- `get_printer_status` returns a compact `details` summary (stage, task, `print_error` and HMS codes in Bambu's dashed form, plate, nozzles with the mounted rack id, AMS trays, external spools, lights, Wi-Fi) instead of the printer's full report and AMS object, which were ~40k tokens on an H2C. `include_raw: true` returns them as before.
- Drop the "both nozzles always match" slicer invariant: a machine profile with different flows per extruder is accepted when each is one of that extruder's variants. Profiles without per-extruder variants still require matching entries, and single-nozzle printers are unchanged.
- Clear errors the way Bambu Studio does (`clean_print_error` with the job's `subtask_id` and the `print_error` being cleared); the bare form left the error in place. A canceled task (`print_error` 0300-400C, kept until the next job) is a warning instead of blocking the next print.
- Accept a printer in `FAILED` (how Bambu firmware reports a stopped or failed job) as idle for a new print, as Bambu Studio does. Like `FINISH` it goes through finished-bed clearance.
- Send Bambu Studio's cloud mapping fields with BambuNetwork prints, built from the checked tray mapping: `ams_mapping` with external trays as -1, `ams_mapping2` as {ams_id, slot_id} (external {254|255, 0}), and `ams_mapping_info` with type, id, colours and the task nozzle from the file's `filament_map`. Without them the printer ran AMS jobs as `use_ams: false`.
- Recognise Studio's Engineering and Cool plate ids (`eng_plate`, `pc_plate`) next to their display names, so files for those plates no longer fail inspection as contradictory.
- Open the printer's cloud channel before a cloud `start_print` as well (subscription, version, certificates): without it the plugin fails the job with -3140 (`ENC_FLAG_NOT_READY`).
- Block printing only on fatal HMS entries (severity 1), print errors and malformed or unknown-severity entries. Serious and common entries no longer block; they come back as `hmsWarnings` (cloud print results include them), like Bambu Studio, which starts prints with them listed and lets the printer refuse a job it cannot run.
- Start the BambuNetwork agent in Bambu Studio's order: register the plugin's `slicer_base64.cer` client certificate (`BAMBU_NETWORK_CERT_DIR`, else Bambu Studio's `resources/cert`, else the bridge runtime) and the client headers before `net.start`. Without them the agent signed in but never connected to Bambu's cloud, so cloud printing and control could not work.
- Run hardware actions unattended by default so agents can drive the printer: print starts, heating, finished-bed clearance and error clearing no longer ask for confirmation. `BAMBU_REQUIRE_CONFIRMATION=1` asks a person for every one of them. File inspection, fresh printer-state, nozzle, material and HMS checks run either way.
- With `BAMBU_DEFAULT_CONNECTION_MODE=bambu_network` and the FULU bridge configured, control commands (clear errors, pause, resume, cancel, speed, light, fans, airduct, AMS, heating, skip objects) go through Bambu's signed cloud path, since firmware 01.08.05+ refuses unsigned LAN MQTT control outside LAN Only and Developer Mode. The bridge client signs in, waits for the cloud connection and subscribes to the printer before sending (the plugin crashes otherwise).

### Fixed
- `camera_snapshot` returns the frame as an MCP image (after a short JSON summary: status, format, size, transport, `savedTo`) instead of base64 inside the JSON text, which overflowed clients' tool-result limits (~180k characters for one H2C frame).
- `get_printer_status` listed the printer's modules a dozen times: bambu-node appends `get_version`'s module list on every reply. The status snapshot now keeps one entry per module (the newest).
- Accept Bambu Studio's idle-hotend `M104 T<extruder> S<target> N0` (multi-extruder pre-cooling, pre-heating and wipe-tower reheat) on every two-nozzle printer (H2D, H2D Pro, X2D, H2C), not only the H2C; two-colour H2D jobs failed inspection on it. The target is still checked like any heater command and the form is refused on single-nozzle printers.
- Apply a manual `filament_map` when slicing for real: Bambu Studio's CLI slices each plate in the plate's own filament map mode (Auto For Flush for a new plate), so the Manual map written to the process profile only reached the project settings and the slicer grouped filaments itself (the result matched only when its grouping happened to agree). The map now goes on the command line (`--filament-map-mode Manual --filament-map`); on the H2C, whose CLI refuses plain Manual ("Group error in manual mode"), as Nozzle Manual with each filament's flow and its own hotend (`--filament-volume-map`, `--filament-nozzle-map`, with the extruders' hotend counts). Checked with the 02.08.02.61 CLI on the H2C ([2, 2], [1, 2], [2, 1]) and the H2D ([1, 1], [2, 2]).
- Slice an H2C with `nozzles_from_printer` for the hotends the printer has: the right extruder's count per flow comes from its normal mounted and rack hotends of the slice diameter (`--extruder-nozzle-count`, `--extruder-nozzle-volume-type`) instead of the profile's six Standard hotends, so the slicer doesn't plan hotends the rack lacks. The per-extruder flows themselves were already read from the report.
- Count a 3MF's filament slots from its model when it has no project filament list (no `Metadata/project_settings.config`): the highest filament the objects, parts and layer ranges are assigned to in `model_settings.config` (`extruder` metadata) and any painted colour regions (`paint_color` / `mmu_segmentation`), as Bambu Studio counts them on import. One filament profile (the default preset or the printer's loaded filament) fills every slot, so a two-part model takes two `filament_colours` and loads two filament profiles; before it was sliced as one slot and two colours were refused. A list of several profiles that covers fewer slots than the model uses is refused before slicing.
- Warn when a mapped AMS slot or external spool is present but reports no filament type (no RFID tag and nothing set on the printer): Bambu Studio shows it as unset, and the declared material is then the only evidence.
- Publish direct LAN commands at Bambu Studio's MQTT QoS: stop, pause, resume (both forms), skip_objects, set_nozzle_temp and set_ctt at QoS 1 (Studio's `publish_json(j, 1)`), so a dropped packet can't silently lose a stop; everything else stays at QoS 0.
- Resume a job paused by an error the way Bambu Studio's error dialog does: when the paused report's `print_error` has a Resume button in Studio's downloaded action list (`hms_action_<serial prefix>.json` in Bambu Studio's `hms` folder, or `BAMBU_HMS_DIR`; Resume Printing, Filament Loaded Resume, Problem Solved Resume), `resume_print` sends Studio's `command_hms_resume` (`resume` with `err`, `param: "reserve"` and the report's `job_id`) instead of the plain resume meant for a person's own pause, and reports the code as `answeredError`. Codes without a Resume button, or without the list, are still refused. A paused processing task (`job_attr` bits 4-7 above 1, such as laser) is refused as in Studio's `check_resume_condition`.
- Close a cleared print error's dialog the way Bambu Studio does: after `clean_print_error`, `clear_hms_errors` sends Studio's `uiop` acknowledgement (`{"system": {"command": "uiop", "name": "print_error", "action": "close", "source": 1, "type": "dialog", "err": "<code>"}}`, `command_clean_print_error_uiop`, sent when its error dialog is confirmed or closed) on the LAN, signed bridge and native routes, and returns the closed code as `closedErrorDialog`. A failed close doesn't undo the clear; it is reported as `uiopError`.
- Check the printer's state before a print start the way Bambu Studio's print dialog does (`update_show_status`), on every print route. Blocked, as in Studio: a required firmware update (`cfg` bit 2 or `upgrade_state.force_upgrade`) or module consistency update, a printer not in FDM mode (`device.type`, a laser or cutting module active), a firmware update in progress, an AMS loading or unloading filament or doing a cold pull (`ams_status`), an AMS setting up (`ams.cali_stat`), no SD card on a model that needs one (P1P, P1S, A1, A1 mini), a LAN-mode printer without storage (unless it has eMMC) or with an abnormal or read-only card, and more filaments than the firmware supports. Listed as warnings, as in Studio: a mapped AMS that is drying, timelapse without storage or with under 20 MB free, and a job that heats the chamber to 40 °C or more (close the door); also an AMS reading RFID tags, which Studio doesn't gate. Uploads, heating and resume are unchanged.
- Judge a print by the printer's own answer to the print command as well as its reports: the direct LAN `project_file` and `gcode_file` replies are matched by the command's sequence id (another client's answer no longer counts), and BambuNetwork prints read the `project_file` answer the network plugin relays (it numbers that command itself, so any answer from the printer after the send counts, as in Bambu Studio). A refusal (`result: "fail"` or a non-zero `err_code`) fails the print with the printer's reason and code ("Failed to start printing job"); the answer is returned as `printerReply`.
- Define report freshness like Bambu Studio's `is_info_ready` (a full report, and a push within `PUSHINFO_TIMEOUT`, 15 s), checked on every safety decision: the state must be restored from a full report at most one full-push interval (3 s) older than the request, a push must have arrived after the request, and the check must run within 15 s of it. A status without the full report it was restored from is refused.
- Restore delta reports onto the printer's last full report the way Bambu Studio does (`json_diff`: a push with `msg` 1 merges into the base key by key, nested objects merge, arrays and values replace; `msg` 0 or none is a full report and resets it). Safety reads used a shallow merge, so a partial delta could replace `ams` or `device` with a fragment and drop fields such as `ams.tray_exist_bits`, skipping the presence check. A safety read now needs a full report plus a push after the request, and deltas with no full report behind them never authorize anything; after more than five of those a full push is requested, as in Studio. The network plugin's `on_message` / `on_local_message` pushes are restored per printer the same way, and command replies seen while polling are kept for reply matching. The status cache merges the same way.
- Ask for a full push in Bambu Studio's form (`pushall` with `version: 1`, `push_target: 1`) and at most once per 3 s per printer (Studio's `REQUEST_PUSH_MIN_TIME`; `BAMBU_PUSHALL_MIN_MS`): a print's back-to-back safety reads sent several within seconds. A read inside that window uses the printer's next push and asks again only once the window has passed.
- Report the printer's own answer to control commands instead of only "sent": pause, resume, stop, clear errors, print speed, airduct, AMS RFID re-read and drying, light, fans, heating and skip objects wait up to `BAMBU_COMMAND_REPLY_MS` (default 3 s) for the reply carrying the command's sequence id, as Bambu Studio matches its acks (a pending-reply map per printer client; on the signed bridge route, the plugin's message events). The result gets `printerReply` (`result`, `reason`, `err_code`), or `null` with a note when nothing came within the wait; a `fail` result or a non-zero `err_code` is an error with the printer's reason. Commands built with bambu-node now take their ids from the server's range as well, instead of bambu-node's own counter from 1.
- Pass the per-extruder slicing options through when `print_3mf` (every connection mode) or `print_3mf_bambu_network` slices an unsliced 3MF itself: both take `nozzles`, `filament_map`, `filament_sources` and `nozzles_from_printer` like `slice_stl`, next to `bed_type` and `nozzle_type`, and pick the machine preset from the resulting nozzle diameter. Before, an auto-sliced dual-nozzle job always got the slicer's own filament grouping and the preset's stock nozzles. A 3MF that is already sliced refuses those options instead of ignoring them.
- Clear errors with Bambu Studio's `clean_print_error` (the job's `subtask_id` and the `print_error` being cleared) on the direct LAN route too, which still sent the bare form that leaves the error in place. One builder makes the command for LAN, the signed bridge and the native helper, from the fresh report the codes check just read, instead of a second status read on the signed route.
- Return non-blocking HMS warnings (serious and common entries, maintenance reminders, a canceled previous task) as `hmsWarnings` on every print route, not only cloud BambuNetwork prints: the direct LAN `project_file` and `gcode_file` prints (`print_3mf`, `print_collar_charm`, `start_print_job`, `upload_file` with `print: true`), the native X2D route, and bridge prints the printer reports as started after an unclear plugin answer. The warnings are those of the last check before dispatch.
- Number every command this server sends from its own sequence-id counter (40000-49999), like Bambu Studio's own range (20000-30000), instead of `"0"` (the id of cloud-originated commands, so printer error replies to it showed in Studio as cloud errors) or 13-digit timestamps that overflow Studio's id parsing.
- Never resend a print whose outcome is unknown: a BambuNetwork print request that got no answer after it reached the bridge (timeout or bridge exit), or a cloud task the printer didn't acknowledge in time (-3130), is reported as possibly started ("Do not send it again", and a no-retry suggestion) after the server checks the printer's reports; when the printer shows the job running it is reported as started. On a timeout the server asks the bridge to cancel the job. Print requests now get 20 minutes before that (Bambu Studio sets no limit; cloud uploads of large files take a while) instead of the 2 minutes of ordinary bridge calls.
- Confirm a print from the printer instead of trusting the send: after a BambuNetwork print returns 0 (the plugin's `start_local_print` returns about 3 s after publishing, with no printer ack) the server reads fresh reports for up to `BAMBU_DISPATCH_CHECK_MS` and reports `status: "success"` only when this job (its name, a new task id, or a printing state on a printer that was idle) is running; otherwise `status: "dispatched_unconfirmed"`, distinct from success, on the direct LAN routes too. A `project_file` reply with `result: "fail"`, this job reported `FAILED`, or a new print error right after the command is an error. Another job's report no longer counts as this one starting. Plugin result codes come with Bambu Studio's explanation.
- Build the direct LAN `project_file` the way Bambu's network plugin does (`start_local_print`, plugin 02.08.02.54) on every model: task options as JSON booleans, `auto_bed_leveling`/`extrude_cali_flag`/`nozzle_offset_cali` as ints, `project_id`/`profile_id`/`task_id`/`subtask_id` as `"0"`, a fresh sequence id from the server's own range instead of `"0"` (the cloud's), the project name as `subtask_name`, `file`, `cfg`, and `bed_type` `"auto"` when unset. The H2/P2S and older payloads no longer differ in shape. The url keeps the forms printers accepted unsigned (`ftp:///…`, `file:///sdcard/…`): the plugin writes `ftp://<file>` but encrypts it on printers that take signed commands, and an H2S rejected an unsigned `ftp://<file>`.
- Open the network plugin's own LAN session before a BambuNetwork LAN print, as Bambu Studio does: callbacks, `connect_printer` (bblp, access code, TLS), wait for `on_local_connect`, request a full push and the version, wait for the printer's report on that session, then install the device certificate. `start_local_print` used to run with no LAN session at all (the plugin publishes the job on it, and signs from that report). A wrong access code or a failed connection stops before anything is sent. `start_local_print_with_record` opens the cloud channel like `start_print`.
- Stop sending unsigned LAN prints a printer will refuse: `start_print`, `start_print_job`, `upload_file` with `print: true` and `print_3mf` over `lan_mqtt_ftps` now read the signing flag from the printer's fresh report the way Bambu's plugin does (`fun` bit 29, else `flag3` bit 4) and refuse before uploading when it is set, since firmware 01.08.05+ turns an unsigned print into HMS 0500-0500-0001-0007, which blocks the next print. With `BAMBU_DEFAULT_CONNECTION_MODE=bambu_network`, `print_3mf` over `lan_mqtt_ftps` goes through the signed bridge. `BAMBU_UNSIGNED_LAN_PRINT=1` opts back in for printers in LAN Only + Developer Mode, which the report doesn't show.
- Dry AMS filament with Bambu Studio's command: `set_ams_drying` sent `ams_control` with `start_drying`/`stop_drying`, which no printer knows. It now sends `ams_filament_drying` exactly as Studio does (mode, filament, temperature, hours, rotation, cooling temperature), takes the filament type, temperature and hours as arguments and the cooling temperature from Studio's filament preset, and accepts AMS HT ids 128-135. A start is refused before sending unless a fresh report shows remote drying support (`fun2` bit 5), an AMS 2 Pro or AMS HT unit and no reason from the printer why it can't dry.
- Select the H2C external spool by holder id: it reports one external holder per nozzle (254 left, 255 right), and a job mapped to 254 now checks that holder instead of rejecting the report as ambiguous. Duplicate, missing or extra holders and other models still reject.
- Match H2C job nozzles to the printer report in physical order: sliced files list the left nozzle first, while the H2C reports its right (main) nozzle as id 0 and its left (deputy) as id 1, so a job with different left and right nozzle types or flows was compared against the wrong nozzle. Explicit nozzle selections and other models are unchanged.
- Let periodic maintenance reminders (HMS 0501-0400-0003-0002/0003/0004/0005/0006/0007/0010: lubrication, cleaning, air filter, hotend latch wear, dusty laser module, as listed in BambuStudio's HMS database) through the print and heating preflight. Every other HMS code, including unknown codes in the same family, and any print error still block.
- Inspect two-colour H2C jobs from BambuStudio 02.08: resolve project filament-variant tables (`filament_self_index` and `filament_extruder_variant`, one row per filament per hotend variant) through the plate's selected variants instead of rejecting them, and accept the idle-hotend `M104 T<extruder> S<target> N0` pre-cooling/pre-heating form, `M620.15 P` nozzle-change pre-cooling, `M620.14 X Y` prime-tower position at filament changes, and the `M9711` timelapse capture command. Every target keeps its independent machine and material limits; other models, other parameters and out-of-bed tower positions remain rejected. Validated offline against a stock 02.08.02.61 two-colour H2C slice; no physical print was run.
- Pick the external spool holder per model, as Bambu Studio does: single-nozzle printers have one holder, which current firmware reports as `vir_slot` 255 (H2S, P2S, X1 series) and older firmware as `vt_tray`; H2D, H2D Pro and X2D have 254 (left) and 255 (right); the H2C's right extruder is fed by the AMS only, so 255 is refused there. External-spool jobs map each filament to its nozzle's holder from the file's `filament_map`, tray mappings accept 255 (and AMS-HT only as 128-135), and the H2 LAN `ams_mapping2` encodes a holder as Studio's `{254|255, 0}`. External-spool jobs on H2S, P2S and X1C firmware that reports 255, and right-holder jobs on H2D/H2D Pro/X2D, were refused before.
- Compare dual-nozzle jobs with the printer through `physical_extruder_map`, as Bambu Studio does, on the H2D, H2D Pro and X2D as well as the H2C: sliced files list the left nozzle first, while these printers report the right (main) nozzle as id 0 and the left (deputy) as id 1. Before, a correct H2D/H2D Pro/X2D job with different left and right nozzles was refused, and one sliced for the mirror-image configuration passed. A file that declares its own map is compared with it; a malformed map fails inspection.
- Check nozzles the way Bambu Studio does: only the extruders the plate's used filaments run on, by diameter and flow. The nozzle material (stainless, hardened steel, tungsten carbide) no longer has to equal the preset's; a filament harder than its nozzle (carbon/glass-filled, PA, PPA, PPS, PLA Glow on stainless or brass) comes back as a warning, as in Studio. An unreliable nozzle report is a warning; an abnormal or unknown nozzle on a used extruder still blocks. On the H2C the right extruder accepts the job when the mounted hotend or any rack hotend matches, and blocks while the rack is being read or when the toolhead and all six rack places are full. Legacy `flag3` flow values other than 1 read as standard flow, as in Studio.
- Address AMS-HT units by their id like Bambu Studio (tray 129 is unit 129 slot 0, not unit 128 slot 1) and check their presence in the top-level `tray_exist_bits` (bit 16 + unit - 128), so a second AMS-HT works and an empty AMS-HT slot is refused. The LAN H2/P2S `project_file` and the native X2D print now send Studio's mapping encoding, as the cloud path already did: external holders as -1 in `ams_mapping` and `{254|255, 0}` in `ams_mapping2` (255 for the one holder of a single-nozzle printer), AMS-HT units as `{unit, 0}`; the native X2D print also gets `ams_mapping_info`.
- Refuse a dual-nozzle job whose AMS slot or external spool can't feed the nozzle its filament is sliced for, before dispatch: each AMS reports the extruder it is bound to (`info` bits 8-11; a Filament Track Switch feeds both only while one is fitted) and the external holders feed 254 left, 255 right. None of the key sets of the installed stock BBL process and filament profiles overlaps a machine profile's, and all 32 installed stock model/nozzle presets load their default process and filament profiles unchanged. OrcaSlicer and FULU installations were not available for real-slicer verification, and no physical print was run. Ported from mcp-3D-printer-server.
- Wait ten minutes by default (`BAMBU_CONFIRMATION_TIMEOUT_MS`, 1000–3600000 ms; other values fall back to the default because Node clamps oversized timer delays to 1 ms) for human hardware confirmation and printer-model prompts instead of the MCP SDK's 60-second request limit, which a person walking to the printer to check the bed could exceed. An unanswered prompt is now reported as a timeout with nothing sent to the printer, instead of claiming the client lacks elicitation support and suggesting `BAMBU_REQUIRE_CONFIRMATION=0`; only a missing elicitation method or capability is reported as unsupported. Covered by MCP stdio regressions with delayed client answers and short configured timeouts; not exercised against a physical printer.
- Name unreadable or malformed profile files in "profile not found" errors so a corrupt profile tree is diagnosable instead of reported as a misspelled name.

## [1.1.1] – 2026-04-29

### Fixed
- **`auto_match_ams` now handles same-SKU different-color filaments.** Previously the matcher keyed only on `tray_info_idx`, so a 3MF needing two GFG02 (PETG HF) trays — one black, one white — would error out as "could not find loaded AMS trays for: GFG02, GFG02" even when both were present. The matcher now joins on `(tray_info_idx, tray_color)` (RGB-normalized; alpha bytes ignored) and tracks already-claimed slots so two requirements can't collapse onto the same physical slot. Falls back to SKU-only matching when the 3MF carries no color or only one tray of that SKU is loaded. Returns a structured `missing` report with reasons (`no_loaded_match` / `color_mismatch` / `exhausted` / `no_sku`) when resolution fails.
- **`get_printer_filaments` retries when AMS data hasn't arrived yet.** The first MQTT push from an idle printer is sparse (model/modules only); AMS data arrives on a second push that often misses the 500ms settle window in `waitForInitialReport()`. Adds a 1.5s retry in `getResolvedPrinterFilamentInventory()` when trays are empty, matching the same retry pattern already used by the HMS resource handler. Validated on Parker H2S (4 loaded trays, all profiles resolved) and Kingpin H2D (no AMS connected — accepted gracefully).
- **HMS resource retries when first status push has no HMS data.** Same root cause — the first MQTT push is sparse (model/modules only); HMS/error fields arrive on a subsequent push. Added 1.5s settle-and-retry in the `printer://{host}/hms` resource handler. Validated on Parker H2S and Kingpin H2D: both returned `hms_errors: 1` (`code: 131099`).

### Added
- **`set_ams_drying` tool** — start or stop the AMS filament drying cycle on heated AMS units (AMS Pro / AMS-HT). Sends `print.ams_control` MQTT command with `start_drying`/`stop_drying` param. Includes input validation (action must be start/stop, ams_id must be 0-3) and 4 new unit tests covering validation and correct command payload shape.
- **`scripts/validate-printer.mjs`** — reusable MCP-over-stdio validation harness that tests HMS resource, set_light, set_fan_speed, set_airduct_mode, clear_hms_errors, get_printer_status, and get_printer_filaments against a live printer. Spawns the MCP server as a child process, sends JSON-RPC messages over stdin/stdout, reports pass/fail per test.
- **`PrinterFilamentInventory` now includes `summary`, `profile_resolution`, `match_confidence`, and `display_name`.** Each tray entry carries a resolution tier (`exact-model-nozzle` / `model` / `generic` / `unresolved`) and a human-readable display name combining sub-brand, type, and color. Top-level `summary` object reports loaded/resolved/empty slot counts and a recommended slot with a human-readable reason. Helps callers make informed `auto_match_ams` decisions without reading raw MQTT status.
- **`scripts/build-charm-3mf.mjs`** — constructs a multi-object source `.3mf` from two STLs (body + face/detail). Volume-based body/face detection (signed-tetrahedron sum, robust to OpenSCAD's uniform facet density). Inline meshes in `3D/3dmodel.model`, per-object `<metadata key="extruder" value="N"/>` in `Metadata/model_settings.config`, plate-level `filament_maps` for H2D dual-extruder routing. Carries `project_settings.config` from a known-good template 3MF. Output is a valid Bambu source project that the CLI parses cleanly; only the upstream slicer-setup SIGSEGV blocks it from being end-to-end useful today.

- **Validation script now tests `get_printer_filaments`.** `scripts/validate-printer.mjs` added as test 8 with live tray output. Also fixed the AMS inspection in the `get_printer_status` test to read the correct raw structure (`data.ams.ams` array) instead of the nonexistent `.trays` path. Accepts "no AMS connected" as a valid printer state.
